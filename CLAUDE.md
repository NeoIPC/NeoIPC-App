# Claude Code — neoipc-app Instructions

This file documents the neoipc-app repository (DHIS2 App Platform application — React/TypeScript). If this repository is checked out as a submodule of the `neoipc-workspace`, the workspace-level `CLAUDE.md` adds additional workspace-specific guardrails (file boundary, cross-repo change order) on top of the guardrails below.

---

## Guardrails

The rules below are the NeoIPC **universal** guardrails, localized to this repository's stack — language-specific examples are adapted to the languages actually used here (primarily TypeScript/React), and code-authoring rules with no referent in this repository are omitted. Rules tagged *(repo-specific)* or *(\<lang\>-specific)* apply only to the repositories that carry them. To add or change a universal guardrail, edit it here and add `<!-- SYNC: propagate to all repos -->` so it is propagated — and re-localized — across every repo when the workspace is next used.

- **Never** put personal names or other identifying information in source code (comments, strings, commit messages, etc.), except in copyright statements and file-header attribution lines (e.g. `Author:`, `@author`, `Copyright (c)` fields).
- **Never** read, write, or access files under `secrets/`, `data/`, or `.env`. This includes listing, globbing, searching, or interacting with these paths in any way — not just reading file contents. If the user provides a path under these directories, use it as-is without exploring the directory.
- **Never** push directly to `main` or `master` on this repository.
- **Never** make HTTP calls to the DHIS2 API or attempt to read JSON files returned from the DHIS2 API. These files contain sensitive surveillance data and are not needed for code-level tasks.
- **Never** put absolute local paths into files that get checked in. Use relative paths or generic placeholders. Local checkout paths are developer-specific and meaningless to others.
- Treat infection definitions in the Surveillance-Toolkit repository as normative. When a conflict exists between code and definitions, **fix the code**, not the definitions.
- **Never** introduce non-permissive dependencies (fonts, libraries, templates). All fonts must be SIL OFL or equivalent.
- **Always** write text files as **LF, UTF-8, no BOM** — and when adding or changing code that writes a file, pin those explicitly rather than trusting the runtime's default. A *mixed* file — part CRLF, part LF — is corrupt rather than merely wrong, and the corruption is invisible in every editor and most diffs, so the point is to keep any single file consistent no matter which tool touched it last. **`.gitattributes` does not save you**: `text=auto` normalizes on *commit*, so a tool writing CRLF into the working tree still yields an LF blob and a clean `git status`. It hides the symptom, not the cause. The CI `text-hygiene` job inspects the working-tree column of `git ls-files --eol` for that reason.

  On the JavaScript side there is nothing further to pin and **no repository-local Prettier config, deliberately**: `@dhis2/cli-style` (a devDependency) ships a Prettier config that already sets `endOfLine: 'lf'`, so the tooling and `.editorconfig` agree. Adding a second config would create a competing source of truth next to the DHIS2 one. Node's own `fs.writeFileSync` does not translate newlines, so a template literal or `JSON.stringify` output is LF already — the traps are in other runtimes, not here.

  Worth knowing rather than acting on: `@dhis2/cli-style` is installed but nothing invokes it — there is no lint or format script, and `yarn validate` runs typecheck, schema-drift and tests only. Wiring it up would adopt DHIS2's full ruleset (80-column, 4-space, no semicolons, single quotes) and reformat most of the codebase, which is a code-style decision separate from text encoding.
- **Always** keep `CLAUDE.md` and `.github/copilot-instructions.md` in sync within this repository. When you modify one, apply the same change to the other.
- **Never** repurpose or re-flag an existing provisioned fixture to satisfy a new requirement — **provision a new one** with the configuration needed. Seeded org units, test departments, fixture patients and demo records exist to hold a *specific* configuration that some test depends on, and that dependency is usually on a property being **absent**: a seeded test department kept deliberately out of a test-unit group is what lets other tests exercise a department that survives test-unit filtering, so adding the flag would silently empty those tests rather than fail them. The absent-property dependency is invisible at the point of change and grep-resistant, which is what makes this dangerous. Adding a new fixture is cheap, additive, and cannot break anything that already passes.
- **Always** reach for **differential observation** before hypothesis-testing when reverse-engineering opaque third-party behaviour (a DHIS2 API response shape, a `@dhis2/ui` component's rendered DOM, a rendering difference). Capture the **complete, unfiltered** state before and after the change — full `outerHTML`, full response body, full object dump — and **diff** them. Testing hypothesised selectors one at a time only ever explores candidates already thought of, and the real answer is routinely an attribute that would never have been proposed; a diff surfaces it whether or not it was suspected, and the diff is usually small enough that the candidates jump out. Corollary: never narrow the capture to the parts matching the current hypothesis — that is precisely how the answer gets discarded before it is ever seen. **For a live web UI, the first move is to reproduce it in a browser and look** — navigate, drive the component, and dump the real DOM and runtime state at each step. That costs minutes and settles questions source-reading cannot, because a component's source describes its **model** while a selector depends on its **render**: reading the source can be entirely correct about which items a component holds in state and still be wrong about which of them exist in the DOM at the moment a test looks. Prefer a **fresh browser profile**, since a persistent one keeps caches and stored state warm and hides exactly the cold-start races worth finding.

  **This applies first and hardest to a failing or hanging e2e test.** When a test fails for a reason that is not immediately obvious from its assertion, **open the page in the browser and look at the DOM before forming any theory** — do not reason from durations, timeout budgets, baseline comparisons, "flakiness", engine differences, or load. Those produce confident, wrong answers: a hang was blamed in turn on CPU contention, output buffering, and an over-tight timeout factor, and a single DOM dump then showed the real cause in one shot — the accordion nests, the same heading resolves on three `.panel` ancestors, and only the innermost has a non-zero toggle, so `.first()` had selected a 0x0 phantom that can never satisfy Playwright's actionability check. Minutes of looking beats an hour of inference, and the inference had already been wrong three times that session. Corollary: identical failure durations across several tests indicate a **shared code path**, not a shared timeout — the timeout is just where every one of them lands.
- **Never** run two e2e/integration suites against the same DHIS2 instance at once — not in parallel shells, not "the previous one is probably nearly done". The stack is a single shared mutable substrate: the Playwright config pins `workers: 1` and `fullyParallel: false` *precisely* because specs register patients, enter events and flush the server cache, so two runner processes defeat that isolation from outside it. The damage is quiet — cross-talk shows up as unrelated-looking failures in whichever run loses the race, sending the reader after a bug that does not exist, and a mid-run kill skips the `finally` teardown and leaves orphaned patients behind. Before launching a run, confirm any earlier one has actually **finished**: an output file whose last line is a section header means it is still going, not that it ended. **Killing a runner does not necessarily stop the run** — cancelling the *task* (closing a shell, Ctrl-C on a wrapper) reliably kills only the process you named, while the children it spawned keep running detached and keep writing to the instance. Verify against the **process list** and kill the whole tree, never against the absence of a task or a quiet output file. Read that list rather than counting it: a browser-automation MCP server and an editor extension's test server both match and are **not** runs. **The check also matches itself**, since the query process carries the pattern inside its own command line — so exclude it and inspect what is left. Never chain the launch off the check with `&&`: that runs on **exit status**, and a counting command exits 0 whether it counted 0 or 400, so the guard reads as protection while blocking nothing. One run at a time, and wait for it.
- **Always** kill a long run the moment its **runner** is found to be broken — a swallowed or over-filtered output stream, a wrapper that buffers until exit, a monitor that cannot distinguish "working" from "hung". Fix the runner and relaunch; that costs a couple of minutes, whereas nursing a blind run costs the whole run's duration and leaves *both* the agent and the user unable to see a hang, a cascade of failures, or a stuck instance. Do **not** compensate with archaeology on the artifacts it happens to leave behind — that is a workaround for a defect that takes two minutes to fix, and it silently reduces what anyone can observe while the run proceeds. Sanity-check that a new runner actually emits a progress line before walking away from it.
- **Always** resolve DHIS2 metadata objects **by `code`**, not by hard-coded UID (`filter=code:eq:<CODE>`). Two reasons, both first-order. **Legibility:** UIDs are opaque and unmemorable — that is precisely why the mnemonic codes exist. `NEOIPC_ADMISSION_TYPE` tells a reviewer what is being driven and can be grepped across the codebase, and makes a wrong-object bug visible in review; `AgBqfnnsUzd` tells them nothing and cannot be sanity-checked by eye. **Portability:** codes are the stable contract the canonical metadata is authored against, while UIDs belong to whichever instance generated them — hard-coding one silently binds the code to a single instance and fails against production, a restore, or a re-generated package, with a "not found" that points at the wrong thing. This applies to data elements, tracked-entity attributes, programs, program stages, org units, option sets and rules alike. Wherever a UID or name must be used instead of a code, state that reason in a comment.
- **Never** adopt a workaround that **reduces what the code actually verifies or does** without asking first and presenting the trade-off. This is distinct from the stuck-investigation rule below: the dangerous case is the workaround that **works**. It compiles, the tests pass, nothing looks wrong — and the loss of fidelity is invisible to everyone but its author. Concrete instance: hitting DHIS2's superuser suppression of the registration `required` indicator and responding with a white-box assertion against `mandatoryFields` (rule *fired*) instead of provisioning a non-superuser test account (what a user *sees*). Green suite, untested code path, nobody informed. Before taking such a route, say plainly: what the faithful solution is, what the workaround stops verifying, and why the faithful one was not taken — then let the user decide. **And never write the resulting limitation up as if it were inherent to the third-party system**: documenting a self-imposed constraint as a discovered property of DHIS2 disguises a decision as a fact, and the next reader will design around it instead of fixing it. Applies equally to narrowing a test's scope, weakening an assertion, skipping a case, and hard-coding what should be derived.
- **Always** bring a stuck investigation to the user rather than iterating alone toward a workaround, once the diff above has not settled it or two attempts at the *same* problem have failed. Show what was actually observed (the diff, the failing selector, the source snippet), state the current hypothesis, and ask — the user knows these systems and repeatedly spots the answer immediately. The failure mode this prevents is not "being slow": it is settling on a **weaker, stranger solution** than the obvious one and then writing a confident justification for it. A degraded assertion, an extra indirection, or a "no reliable way exists" conclusion are all signals to stop and ask. Pairs with the push-back guardrail below — both say the goal is the *right* answer, not an independently-reached one.
- **Always** push back when evidence contradicts the user's suggestion or implied assumption. Do not defer to the user's position when authoritative sources (AMA Manual of Style, protocol definitions, language specifications, etc.) say otherwise. Present the evidence clearly and let the user decide.
- **Always** consider both personal data protection (GDPR) and organizational/reputational concerns when making decisions about data shared between partners, published in reports, or exposed through APIs. Small cell counts in shared reports can expose which departments had specific rare pathogens or resistance patterns.
- **Always** treat accessibility and long-term archivability of generated user-visible or publicly published documents as explicit, first-class goals of the NeoIPC Surveillance Toolkit — not optional polish. Wherever a NeoIPC tool produces a document a person reads or that is published (reports, certificates, web UIs), enable and maintain **both** — **to the extent the toolchain can genuinely achieve them**: accessibility conformance (WCAG via `axe` on HTML, tagged PDF with alt text on every figure and decorative images marked as artifacts, accessible web UIs) and long-term archival compliance (PDF/A). **Never declare a conformance the output does not actually have.** A standard asserted in metadata but not met is worse than claiming nothing, because every downstream consumer trusts the assertion — e.g. declaring PDF/UA under a document class that cannot emit tagged structure yields a file that says it is accessible while every heading is ordinary paragraph text. When a property is currently unreachable, say so where the setting lives, record what would unblock it, and declare only what holds. When adding or changing such output, keep the properties that do work working; prefer formats and settings that preserve them, and treat a regression in tagging, alt text or PDF/A conformance as a defect.
- **Always** treat linguistic, script and cultural diversity as an **asset and a first-class goal**, never a cost to be justified before it is admitted. The set of supported languages is a **floor, not a ceiling**, and where a tooling limit happens to fall on non-Latin scripts or non-Western conventions — no complex-script shaping, no bidirectional text, a name or date format that assumes one region — treat it as a **defect to schedule**, not a boundary to design around. Two limits keep this honest, and they cut against opposite failures. **Never declare support the output does not have**: listing a language that renders as broken glyphs, or asserting a conformance that is not met, misrepresents the project to exactly the community it was meant to include, so "supported" has to mean *renders correctly*. But **incomplete is not the same as misdeclared** — a partly translated document, a script served in one output format while another is still wrong, or a language marked *preview* are all better than nothing, provided the label matches what is inside. So: **ship what works, name what does not, and record what would unblock the rest.** Waiting for a perfect solution serves those communities no better than overclaiming does, and it is the more common of the two failures.
- **Never** use deprecated or outdated APIs. Before introducing a function from a third-party package or a base library, verify it is current. When a replacement exists, use the replacement. When unsure, check the package's `CHANGELOG.md` / release notes rather than assuming.
- **Always** read the upstream source directly when you need a definitive answer about a third-party system's behaviour (DHIS2 in particular, but also R / tidyverse packages, Quarto, Pandoc, .NET runtime, etc.). Docs, release notes, and changelogs are known to be unreliable for some of these projects — the source is the ultimate authority, the written reference is a convenience shortcut. Where a read-only checkout of the upstream project is to hand, read it there rather than over the network.
- **Always** parse a structured format with its own parser rather than a regex over the source — JSON via `JSON.parse`, gettext catalogues via a PO library. A regex reads text; the parser reads the document, and the difference surfaces as silent corruption rather than an error: a regex sweep over structured source has here mis-detected nesting and deleted lines it was not aiming at. Use a regex only where no parser exists, and say so at the call site. Before concluding a tool does not diagnose something, **check its log levels** — a diagnostic below the tool's default threshold is never emitted, which is how seven dead cross-references shipped in the surveillance protocol behind a green build.
- **Always** verify upstream claims now, not later. When a plan or recommendation depends on a fact about a third-party system's behaviour, read the source as part of the planning step; do not write "verify at implementation time" or "TBD against upstream" and move on. Deferred verification compounds — each unresolved fact is an attack surface for later wrong implementation. Pairs with the "read the upstream source directly" guardrail above.
- **Always** verify factual claims in design notes and task files against the actual source before propagating them. Treat "X does Y" descriptions in repo documentation as a hypothesis to verify by reading the function or module, not as ground truth — these documents can carry stale or wrong claims that survive long enough to look authoritative. When the claim turns out to be wrong, fix the documentation in the same commit.
- **Always** re-read iteratively-edited documents end-to-end before marking them done. After several rounds of edits to a long document (plan files, design docs, multi-section task files), proactively read the whole thing to catch sentences that contradict later edits, file/path references that no longer match the current model, summaries that drifted from the detail, deferred-section markers that disappeared, naming-scheme drift between sections. Don't make the user point each one out individually.
- **Never** dismiss identified inconsistencies as "cosmetic" when a rename window is already open (pre-alpha, release prep, planned breaking change in the same area). The cost-benefit changes the moment a rename for anything else in the same family is proposed; the right default in that window is to fix the inconsistency in the same pass.
- **Always** treat test evidence asymmetrically: **a red run proves a failure exists; a green run proves nothing.** Green means only that *this* run, on *these* assertions, did not hit a defect — it is never evidence that a safeguard is unnecessary, because the safeguard may be exactly what kept it green, and because auto-waiting assertions (`expect` in Playwright) rescue any assertion that *flips* state while silently passing the ones that are already true in the stale state. The burden of proof therefore sits on **any** change to a wait, guard, retry or workaround — **adding one as much as removing one** — and a passing test does not discharge it in either direction. Adding is the more insidious case, because a green run after adding a fix feels like confirmation while proving only that the symptom stopped appearing: the change may have masked the defect, merely shifted the timing, or fixed something adjacent while the real cause waits to resurface elsewhere. That is precisely how workarounds accumulate — each was added when a test went green, none had its mechanism established, and they then survive for years because nobody can safely tell which is load-bearing. **If you cannot PROVE the mechanism, you have a hypothesis, not a fix — say so in the comment.** Naming one is not proving one, and the distinction is the whole point: a plausible mechanism is trivially easy to produce and manufactures confidence without evidence. In a single session here, the same failure was confidently attributed in turn to CPU contention, to output buffering, and to an over-tight timeout factor — three named mechanisms, all false, each argued fluently — before a thirty-second DOM dump showed the real one. Proof means a demonstration that would have come out differently had the explanation been wrong: the upstream source read to the line that settles it, a probe whose output can only occur under that explanation, or a test that goes red without it. "It is consistent with the symptom" is not proof; a great many wrong explanations are.
- **Never** let a test — or the harness around it — **change the system under test. Tests observe behaviour; they do not intervene in it.** Three things remain legitimate: **reading** state (the DOM, a scope or store, a response body, a log), **driving** the software the way a real user or caller does (clicking, typing, calling its public interface), and **provisioning fixtures** through that same public interface. What is barred is reaching *inside* the running system to make it do something no user could — calling an internal service method, replacing or wrapping a function, forcing a recomputation, or writing to internal state to reach the condition an assertion wants. The distinction is not "does it use the debugger API" but **read versus write**: `page.evaluate` that dumps component or store state is observation; `page.evaluate` that calls into the app to change it is interference. **The failure mode is that it works.** The suite goes green, nothing looks wrong, and the assertion is now passing because the harness produced the state rather than because the software did — so the test no longer measures the software at all, and the defect it was meant to catch ships. The tempting forms here are forcing a re-render or a refetch so an assertion sees fresh data, and reaching into the DHIS2 runtime to seed or invalidate a query's cache: both manufacture the state the app was supposed to reach on its own, and a suite that does it is green against data the app never actually loaded. When the software is hard to observe, the answer is a better *observation* (watch its network traffic, read its state, instrument a copy you build yourself), never a nudge. The sole admissible exception is an **explicitly opt-in diagnostic** — off by default, never active in a normal run, never something an assertion depends on, **and behaviour-transparent**: if it wraps a method it must be a pure passthrough that alters no argument, return value, timing, or effect, so it observes without changing what it observes (a "diagnostic" that drops an argument or delays a call is interference wearing a label).

  **Reading the source is weakest exactly where it feels strongest: asynchronous, event-driven, non-linear code.** Source reads top-to-bottom; it executes interleaved. Promise chains, React effects and state batching, the data runtime's fetch-and-cache cycle, and native-vs-framework microtask queues all mean the text cannot show you *when* something happens relative to something else — and "when" is usually the entire question. Two ways this misleads even when the reading is correct. First, **ordering is invisible**: an effect or continuation that "obviously" runs before the next observation may not, and the code offers no clue either way. Second, and more dangerous, **the source can answer a different question than the one asked** and look decisive doing it — a component's source will tell you truthfully which items it holds in state, while the question was which of them are in the DOM at the instant a selector runs. The code is about the model; the question is about the render. So in async code, treat a source-derived answer as a **hypothesis about ordering that still needs observing**: instrument it, dump the live state, or timestamp the sequence. Prefer evidence that carries its own timeline — a console/network trace, a probe printing state at each step — over any argument of the form "this must happen before that". Discharge the burden one of two ways: derive the answer from the **upstream source** (what does the code actually depend on?), or construct a test that would **fail if your belief were wrong** — one that goes red without the change if you are adding, or red without the removed thing if you are removing — then run *that*. Generalising from whichever test you happened to run is how three separate load-bearing layers got deleted here in one session, each on the strength of a single green cascade test, and each restored only after a red run elsewhere exposed it. Corollary: this is cheap to get right — the stack is synthetic, so an **isolated single test** plus a targeted browser session costs minutes and settles what hours of inference will not.
- **Never** edit a checked-in file through a generated script (a Python/PowerShell one-liner doing string replacement, `sed -i`, and the like). Use the editor's own edit operation, one change at a time. Two reasons, both first-order. **Reviewability:** a scripted edit shows the user the *script*, not the change — they cannot see a diff, cannot follow what is happening to their code, and the actual modification is hidden behind a layer of abstraction they did not ask for. **Correctness:** string-replacement surgery on structured text repeatedly mangles files here — it has silently dropped adjacent code, left orphaned declarations, and produced edits whose damage only surfaced later in a failing test. Both failure modes have occurred more than once in a single session. This applies to bulk edits too: several individually-visible edits beat one invisible sweep. The exception is a *generated* file that is never reviewed by hand.
- **Never** use unexplained acronyms or initialisms in code comments, doc comments, or documentation prose — write "Tracker Capture", not "TC". They cost the writer nothing and cost every subsequent reader a lookup, and the reader is usually someone with less context than the author had. Established domain terms that the repository defines somewhere (`NEOIPC_CORE`, DHIS2, SSI/BSI/HAP/NEC as infection types) are fine; ad-hoc contractions of product or component names are not.
- **Always** number the items of a list, or of a set of cases, conditions or alternatives, that the text later refers back to, and refer to them by that number — "requirement 2", "case 3", "proposal 1" — never as "the first", "the second", "the former" or "the latter". A positional reference makes the reader count back through the text, and it turns ambiguous as soon as anything between the list and the reference enumerates something else. Where the members already carry numbers of their own, use them ("types 1 and 2", "slot 3") rather than "the other two". This applies to documentation, comments, and commit and pull-request messages alike.
- **Always** call what causes an infection an **infectious agent** — never a *pathogen* or an *organism*. A healthcare-associated infection can be caused by an infectious agent that is not considered a pathogen, and by one that is not an organism at all (a virus, a prion), so either word misstates what NeoIPC records. This holds for prose, user-facing strings, documentation, comments and every new identifier, and compounds follow it ("infectious-agent group"). Three things keep their wording: an established defined term that contains one of the words, such as the NeoIPC protocol's *recognized pathogen* (the category set against *common commensal*); a quotation of an external source; and an existing identifier that is a stable contract — a DHIS2 code such as `NEOIPC_BSI_PATHOGEN_1`, a column or file name other code or users depend on — which changes only in a deliberate, coordinated rename, never in passing.
- **Never** write filler comments — comments that describe absent behavior ("not currently used"), restate the obvious, or hedge ("maybe this is needed?") add no information. The default is no comment; reserve comments for hidden constraints, subtle invariants, surprising behavior, or workarounds for specific bugs. If a property's existence is unclear without a comment, the property is misnamed, misplaced, or shouldn't exist — fix that instead.
- **Always** write doc comments on public API surface (TSDoc / JSDoc on exported functions, components, hooks, and types) and targeted explanatory comments at non-obvious design points as part of the same change that introduces the code — don't defer to a "doc-comments sweep" follow-up. Pairs with the "no filler comments" guardrail above: comments must add information, AND the ones that are warranted must land in-band, not later.
- **Never** predict the future in code comments. Speculative commented-out code, `// TODO: when X happens, do Y` notes, or any forward-looking text describing not-yet-decided changes belongs in the project's task tracking, not in checked-in source. Source comments describe *what is*, not *what might be*.
- **Always** write the *outcome* of a decision into a checked-in file rather than the path to it — and where the path matters, **ask rather than decide alone**. A comment and a document state **what is true now and why**, in the present tense. A superseded value (`// this was 10 mm`), a note of when or by whom something changed, and above all **the loop that produced the answer** — a correction taken, a review acted on, a maintainer's adjustment — are dead weight the moment the next change lands, and nobody reading the file later is interested in the circles that preceded the right thing. The chronology is git's, and the reasoning for a change *as a change* belongs in the commit message. **But a failure is sometimes exactly what the next reader needs**: an alternative that looks attractive and is not, a measurement that inverted the expectation, a trap already walked into once. Those can be worth more than the outcome alone — and which ones qualify is **the maintainer's call, not yours**. So leave it out by default and **ask** when you think a particular one earns its place, instead of deciding either way on your own; a sweep that strips them all is as wrong as one that records every wrong turn. When one is kept, write it in the present tense as a standing property ("X is not used, because Y"), never as a narrative of having tried it. Pairs with the no-future-prediction guardrail above: a checked-in file describes *what is*, and what it used to be is a question to raise rather than to settle unilaterally.
- **Never** reference internal project-tracking identifiers in checked-in source or its comments — milestone or phase labels (`M3`, `Phase 2`), plan-decision numbers (`decision 8/9`), task-file or plan-document names, sprint names, and the like. They are opaque to anyone reading the code without the current planning context, and they go stale the moment the plan moves on. State what the code *does* and why in terms intrinsic to the code; the milestone/task linkage belongs in the project's task tracking and the commit/PR message, not in the source. Marking genuinely provisional code as such is fine — but describe the state intrinsically ("currently not handled", "deferred", "scaffold") rather than naming the milestone that will retire it. Pairs with the no-future-prediction guardrail above.
- **Never** leave placeholder stubs (a function or component whose body is just `throw new Error('not implemented')` or similar) in source as scaffolding for future work. A function or component that exists only to throw because the real implementation "comes later" is dead code. Delete it; the planned work belongs in the project's task tracking, not in checked-in source.
- **Never** add a `Co-Authored-By` trailer crediting an **AI, an IDE or any other tool** — the user does not want AI co-author attribution, and a tool is not a co-author. **Human co-authors are the opposite case and must be preserved.** A contributor's trailer is real attribution, is sometimes a licence condition rather than a courtesy, and must never be stripped when squashing a pull request or rewriting a commit message — including trailers a platform adds on a contributor's behalf.
- **NEVER merge a pull request without the user's explicit approval of that specific merge, and never before every review on it has arrived and been addressed.** This is not a formality and not a judgement call. Say what you propose to merge and wait for a plain "yes, merge it" naming that request; anything less is not approval. **The following are NOT approval, and each has been mistaken for it:** "move on", "go ahead", "now", or any instruction to continue the surrounding work; your own belief that the change is finished, tested, or urgent; approval of an *earlier* merge in the same session; and — most dangerously — an **administrator override**. An override exists to bypass one mechanical gate you have already explained; it says nothing about whether the change should land, and treating "the gate failure is expected" as "the pull request is ready" is precisely how a defect reaches `main`. **Approval is anchored to the commit it was given for.** A push invalidates it — what was approved is no longer what would merge, however small or review-driven the new commits are — so re-confirm, naming the new head. Spending an approval given at one commit on a later one is the same inference as spending an earlier merge's approval, which is already barred above. **Wait for the reviews, including the automated ones.** A review that is still running is a review you have not read: check for it immediately before merging, not when you opened the request, and address every finding first. **Wait for every reviewer, not the first to answer** — where more than one reviews a request, a poll that stops at the first arrival merges past the slower one, which is this guardrail's own failure reached by a different route. **Ask in the working session, never on the forge:** a review posted from the maintainer's own account may be another agent rather than the maintainer, so it can neither grant approval nor be argued with about one. Merging past a review is unrecoverable in a way that waiting never is — it published a volunteer's name and e-mail address to a public repository, which then cost a history rewrite, a temporary weakening of branch protection, and a support request to a third party, for a finding the running review had already made. When in doubt, do not merge; ask.
- **Never** create a merge commit, and **always** squash-merge — a pull or merge request lands as exactly **one** commit, and a non-linear history is not permitted anywhere in this project. This is enforced in the forge settings rather than left to memory: merge commits are disabled, squash merging is enabled, the source branch is deleted on merge, and rebase merging is disabled too. GitLab projects express the same shape as `merge_method: ff` with `squash_option: always`. **Compose the squash message; never accept the pre-filled one.** The forge seeds it with every individual commit message from the branch, which is work-in-progress narration rather than a description of what landed. Replace it with one message that says what the change delivers and why, at the thematic level — naming a file or function only where it anchors a point, never as an inventory of everything touched. On a single-commit branch the pre-filled message is that commit's own and can be kept, but read it: the squash is the only point at which a co-author trailer naming a tool can be removed. **These rules interlock; read the cluster rather than one member of it.** The squash message you compose is still bound by the rules against enumerating every individual change and against process meta-commentary, and must not gain an AI or tool `Co-Authored-By` trailer — while any **human** co-author trailer the branch carries must survive the squash; what you may do to a branch that is already under review is governed separately by the force-push rule.
- **Never** call out the review process in commit / pull-request / squash-merge messages. Reviews are a normal part of the development workflow — what lands is just code that landed. Drop "review-driven deltas" sections, per-round citations ("round 7 fixed X"), "fixes from Copilot feedback" framings, and similar process meta-commentary. That information belongs in the review threads, not in permanent history. **The corollary is not that credit is optional**: where a review found something, say so *in the thread*, which is the place that keeps it. A message constrained from naming the review should describe the defect rather than the discovery, and never imply the author traced what a reviewer handed them.
- **Never** enumerate every individual change in a commit / pull-request / squash-merge body. Listing every fixed bug, renamed function or per-file tweak bloats the message without adding context. Describe what the change delivers at the *thematic* level — features, capabilities, design decisions — at the granularity where a future reader can quickly understand the scope. Specific file paths or function names earn their place when they anchor a thematic point, never as an inventory.
- **Never** use a bare `#N` cross-reference for an issue or work item that lives in a **different repository or tracker**. A forge auto-links `#N` to issue/pull-request *N of the repository you are writing in*, so a `#5` meant for an item elsewhere — another NeoIPC repository, or the GitLab tracker some of them use — silently cross-links and notifies an unrelated issue there. Write the repository and number ("neoipc-dhis2 work item 5") or the full URL. Bare `#N` is correct *only* when it genuinely means an issue or pull request in the **same** repository. GitHub and GitLab both auto-link this way, so neither is a safe exception. This is a recurring correction — check every `#N` before posting.
- **Always** squash a pull request raised from the **`weblate-app`** push branch, like every other pull request here, and **refuse it if the branch carries more than one commit**. One commit is what makes a squash safe: it reproduces that commit's patch exactly, so Weblate still recognizes its own work as merged. Several fuse into a patch matching none of them, and Weblate replays work it can no longer prove had landed, conflicting instead. The single-commit property is a Weblate setting rather than a law, so it is checked at merge time. **Read the pre-filled message before confirming**: on a single-commit branch it is that commit's own message and needs no rewriting, but Weblate's `append_trailers` credits its own service account as a co-author, and the squash is the only point where that trailer can be dropped — a tool is not a contributor. **Delete the head branch when the pull request merges** — mechanism, not tidiness: merging rewrites the commit's SHA, so the pushed `weblate-app` tip stops being an ancestor of `main`, Weblate's next push is rejected as non-fast-forward, and because *Lock on error* is on that rejection **locks the component against translators**. *Automatically delete head branches* is enabled here, and the component has *Push on commit* **off** — otherwise Weblate pushes at exactly the moment its Squash add-on has rewritten, and so invalidated, the already-pushed tip. **The repository owns `i18n/en.pot`; Weblate owns every `i18n/<lang>.po` and is their only writer.** `d2-app-scripts i18n extract` writes only the template, and the localized output it generates under `src/locales/` is untracked, so there is nothing to restore after a run and no regeneration commit after a drain. Do not hand-edit a catalogue: the change is either overwritten by Weblate's next write or turns into a conflict — and a pull request that does it is **rejected by CI**, by the `catalogue-ownership` job in [`.github/workflows/build-and-test.yml`](.github/workflows/build-and-test.yml), which fails when any `i18n/*.po` in the pull request carries a commit whose committer is not Weblate. So this is enforced rather than merely stated; the failure names each offending file and how to restore it. **Exactly one repository-side edit of those files is on record as legitimate, and it is the last.** The commit that introduced this rule also rewrote all nine catalogue headers, because each had been created from the template and inherited the generator's metadata — a tool name where the project belongs, and timestamps older than the files carrying them. That was possible only in the handover window: the component was registered but had never written to this repository, no drain had happened, and the sole existing translation was already here. The window is closed, and it does not reopen — after it, a repository-side edit of `i18n/<lang>.po` is a defect however well-intentioned, header hygiene included. Anything of that kind goes through Weblate. *(repo-specific)*
- **Always** give a source string a Weblate **explanation** wherever it exposes a translator to markup, a placeholder or an identifier that must survive translation unchanged — an interpolated `{name}`, a format token, an embedded tag — saying which part is fixed and which is theirs to translate. Explanations live only in Weblate's database, so they cost the catalogue nothing and survive every `msgmerge`. **Remove the exposure where the code allows it, and explain it where removing it would cost more than it saves**: a value the user never sees translated belongs outside the string, but a placeholder that has to sit mid-sentence for the grammar to work cannot be moved, so it earns an explanation instead. A quality check rejects the mistake after the fact; the explanation is what prevents it. *(repo-specific)*
- **Never** put long-lived guidance in per-machine local memory (e.g. Claude Code's `~/.claude/.../memory/`) — it does not follow the user across machines. Coding rules, communication preferences, domain conventions, and recurring corrections belong in this `CLAUDE.md` (and its `.github/copilot-instructions.md` sibling) so they travel with the repo. Reserve local memory for genuinely ephemeral session context.
- **Never** point a checked-in file at a Claude Code (or other agent tool's) **per-machine session artifact** as a reference — a saved plan under `~/.claude/plans/`, a transcript / tool-result under `~/.claude/projects/`, or per-project local memory. These live in per-machine local state: they do not sync across the user's machines and are invisible to other developers (and to an agent on another checkout), so a `See plan file: ~/.claude/plans/foo.md` pointer in a committed task or planning document (or any other committed doc, source comment, or commit message) is a dead link for everyone but its author on the one machine that has it. **Inline the durable content** — the plan's decisions, rationale, and build sequence — into a committed document in this repository instead of citing the local path. Merely *describing* such a path where the path itself is the subject (e.g. documenting which paths an agent tool is permitted to access) is fine; the rule is against citing one as a source of truth. Pairs with the no-absolute-local-paths and no-per-machine-local-memory guardrails above.
- **Never** modify the user's global git config (`git config --global ...` / `~/.gitconfig`) as a workaround for a transient problem. For network disconnects, slow clones, or intermittent failures, **retry** — the failure is usually elsewhere and a config tweak persists across every repo on the machine. For genuine repo-specific tuning, use `git config --local ...` or a one-shot `-c key=value` flag on the command. Examples to avoid: `core.compression=0` (kills compression for all future git operations), `http.postBuffer` bumps (only relevant for HTTP-1.1 push edge cases). If a genuine global change is needed, surface it to the user first with the specific reason and the persistent cost.
- **Never** force-push to a branch that has an open pull request under review. Rewriting already-pushed history mid-review is hostile to reviewers — it discards their in-progress review, breaks the anchoring of existing review comments to lines and commits, and hides what actually changed since they last looked. Push follow-up commits instead; because merges are squash-merged, the intermediate commits collapse into one on merge, so a clean final history costs nothing. Force-pushing is acceptable only on a private WIP branch that has not been shared for review.
